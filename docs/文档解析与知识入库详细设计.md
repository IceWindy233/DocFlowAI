## 1. 文档目的

本文档描述 DocFlow AI 从原始公文文件到可检索知识对象的完整处理方案，重点回答以下工程问题：

1. 如何稳定处理 DOC、DOCX、WPS、PDF、扫描件、表格和混合图文文件；
2. 如何在 Docling、Marker、OCR、VLM 和 ColPali 等能力之间选择处理路线；
3. 如何定义不依赖具体解析器的统一文档数据模型；
4. 如何识别公文事项、主文、复函、附件和不同版本；
5. 如何处理重复文件、旧版文件、解析失败和低质量结果；
6. 如何生成适合关键词检索、向量检索、事实核验和页面引用的 Chunk；
7. 如何保证入库任务可重试、可追踪、可审计和可增量更新；
8. 如何为公文撰写、公文审核和检索问答提供一致的知识底座。

本文档不定义具体 Agent Prompt，也不展开三大业务功能的交互细节。

## 2. 设计目标

### 2.1 功能目标

- 支持批量扫描文件系统中的历史公文；
- 支持 DOC、DOCX、WPS、PDF、XLS、XLSX 和常见图片格式；
- 支持可搜索 PDF 和扫描 PDF 的差异化处理；
- 支持文档级、页面级、区块级和表格单元格级定位；
- 支持复杂表格、表单和混合图文页面的结构化增强；
- 在知识入库阶段为复杂页面建立 ColPali 视觉多向量索引；
- 支持文本、表格、页面图片和视觉向量通过统一 `page_id` 回源；
- 支持公文事项、文档角色、版本状态和权威等级识别；
- 支持精确去重和近似重复检测；
- 支持结构化文本、表格、页面图片和视觉向量的多表示存储；
- 支持全量入库、增量入库、单文件重解析和索引重建；
- 支持人工修正解析结果和分类结果；
- 支持文档撤回、删除和索引同步失效。

### 2.2 非功能目标

#### 可追溯

任意 Chunk、实体或回答证据都必须能够追溯到：

```text
知识对象
→ 文档版本
→ 原始文件
→ 页码
→ 页面区域
→ 解析运行记录
```

#### 幂等

同一文件重复提交，不应重复创建文档、Chunk 或向量。任务重试不得产生多份有效记录。

#### 可恢复

长时间运行的 OCR、解析和 Embedding 任务应支持断点恢复。单个文件失败不能导致整批任务回滚。

#### 可替换

解析器、OCR、Embedding、Reranker 和视觉检索模型通过适配器接入，不将核心数据结构绑定到具体供应商。

#### 安全

原始文件、页面图片、解析文本、日志和索引遵循相同权限。云端解析默认关闭。

#### 可评估

每次解析运行记录解析器版本、配置、质量得分、耗时和失败信息，支持同一文档不同解析路线的离线对比。

## 3. 语料规模与容量基线

当前目录基线为单一组织的历史公文集合：

- 规模：数千个文件，总量 GB 级；
- 文种：按“请示”“函”等事项目录组织；
- 格式：以 DOC、DOCX、WPS 和 PDF 为主，含少量 XLS/XLSX、图片和压缩文件；
- 扫描件：相当比例的 PDF 为扫描件，需要 OCR；
- 冗余：存在较多完全重复文件和 Office 临时文件。

容量设计按以下增长假设进行，不作为性能承诺：

- 初期支持 1 万个文件和 10 万页以内的单组织知识库；
- 文本、页面图片和向量分开存储；
- 原始文件和派生文件不写入 PostgreSQL 大字段；
- 页面图片、解析 JSON 和导出产物进入对象存储；
- PostgreSQL 保存业务元数据、关系、Chunk、实体和向量索引元数据。

## 4. 术语与标识符

### 4.1 术语

| 术语 | 含义 |
| --- | --- |
| Source | 一个文件来源，例如受控目录、上传任务或外部系统 |
| Source File | 在某个来源中发现的物理文件记录 |
| Blob | 由 SHA-256 唯一标识的文件二进制内容 |
| Document | 业务意义上的逻辑文档 |
| Document Version | 逻辑文档的某个历史版本 |
| Case | 一个完整公文事项 |
| Parse Run | 对某个文件版本执行一次解析的运行记录 |
| Normalized Document | 与具体解析器无关的统一文档对象 |
| Block | 页面内的标题、段落、表格、图片等版面区块 |
| Chunk | 面向检索构造的知识片段 |
| Publication | 一次可原子切换的索引发布版本 |
| Authority | 文档版本作为业务依据的权威等级 |

### 4.2 标识符策略

所有业务主键使用不可推断的 UUID/ULID。以下内容使用稳定哈希：

- `blob_sha256`：原始二进制精确哈希；
- `normalized_text_hash`：标准化正文哈希；
- `page_image_hash`：页面图片哈希；
- `chunk_content_hash`：Chunk 内容及元数据哈希；
- `embedding_input_hash`：模型名称、模型版本和输入内容联合哈希。

推荐标识符：

```text
src_       数据源
file_      来源文件
blob_      二进制对象
case_      公文事项
doc_       逻辑文档
ver_       文档版本
run_       解析运行
page_      页面
block_     页面区块
table_     表格
chunk_     检索片段
entity_    实体
rel_       关系
pub_       索引发布
job_       入库任务
```

ID 不包含组织、文号、年份或文件名，避免业务信息泄露并减少字段变更造成的主键变化。

## 5. 总体处理架构

```text
数据源
  ↓
File Discovery
  ↓
Preflight & Security Check
  ↓
Fingerprint & Exact Dedup
  ↓
Case Seed & Role Hint
  ↓
Parse Route Decision
  ↓
Convert / Render / OCR / Parse
  ↓
Parse Quality Gate
  ├── 合格 → Normalize
  ├── 不合格 → Fallback Route
  └── 仍失败 → Human Review / Quarantine
  ↓
Complex Page Detection
  ├── 普通页面 → 保留结构化文本和页面图片
  └── 复杂页面 → Table/VLM Enhancement + ColPali Multi-Vectors
  ↓
Metadata & Entity Extraction
  ↓
Case Linking & Version Resolution
  ↓
Chunking
  ↓
Keyword / Dense / Visual Index
  ↓
Atomic Publication
  ↓
供撰写、审核、问答使用
```

### 5.1 逻辑组件

| 组件 | 职责 |
| --- | --- |
| Source Scanner | 扫描目录、上传区或外部数据源 |
| Manifest Builder | 构建来源清单和文件快照 |
| Preflight Inspector | 文件格式、安全、页数和文本层预检 |
| Dedup Service | 精确去重、别名管理和近似重复候选生成 |
| Route Planner | 选择转换、解析、OCR 和视觉处理路线 |
| Converter Workers | DOC/WPS/XLS 等旧格式转换 |
| Parser Workers | Docling、Marker、OOXML 等解析适配器 |
| OCR Workers | 页面渲染、方向校正、OCR 和置信度计算 |
| Complex Page Classifier | 识别复杂表格、表单和混合图文页面 |
| Multimodal Enricher | 生成表格多表示、VLM 结构结果和视觉页面表示 |
| Quality Gate | 解析质量评分、异常检测和降级决策 |
| Normalizer | 生成统一文档对象 |
| Classifier | 文种、角色、密级和版本提示识别 |
| Case Linker | 将文档归入事项并构建业务关系 |
| Version Resolver | 识别版本链和权威等级 |
| Chunk Builder | 构造多粒度检索片段 |
| Indexer | 写入关键词、向量、关系和视觉索引 |
| Publisher | 原子发布可查询索引版本 |
| Review Console | 人工修正分类、版本、关系和解析结果 |

### 5.2 进程划分

MVP 可以拆分为：

```text
API Process
Scheduler Process
CPU Worker Pool
GPU Worker Pool（可选）
Index Worker Pool
PostgreSQL
Object Storage
Redis/Task Queue
```

CPU Worker 负责文件预检、格式转换、结构解析、规则抽取和切块；GPU Worker 负责深度 OCR、VLM、Embedding、Reranker 或 ColPali。没有 GPU 时允许全部使用 CPU 或外部模型网关，但任务状态和接口保持一致。

### 6.1 数据源类型


```yaml

  - "**/*.doc"
  - "**/*.docx"
  - "**/*.wps"

  - "**/*.xls"
  - "**/*.xlsx"

  - "**/~$*"
  - "**/.DS_Store"
  - "**/*.lnk"
follow_symlinks: false
default_confidentiality: restricted
cloud_processing_allowed: false
```

### 6.3 文件发现规则

文件发现阶段只读取文件元数据和计算必要哈希，不解析正文。

记录字段：

```text
source_id
relative_path
filename
extension
detected_mime_type
size_bytes
mtime
ctime（仅用于辅助，不作为业务时间）
inode/file_key（若可用）
blob_sha256
discovered_at
```

规则：

1. 不跟随符号链接；
2. 不将绝对路径提供给普通业务用户；
3. 文件扩展名与 MIME 不一致时以内容检测为准，并产生警告；
4. 文件路径采用 Unicode NFC 标准化用于比较，但保留原始显示名称；
5. 路径大小写比较遵循来源文件系统规则；
6. 文件移动但内容未变化时创建新的 Source File 别名，不重复解析 Blob；
7. 同一路径内容变化时创建新的文件修订记录，不覆盖历史状态；
8. 默认不自动解压 ZIP/RAR，压缩包进入隔离队列，后续由显式策略处理。

## 7. 入库任务与状态机

### 7.1 任务类型

| 类型 | 用途 |
| --- | --- |
| FULL_SCAN | 全量发现并处理新增/变更文件 |
| INCREMENTAL_SCAN | 对比快照后处理变化 |
| FILE_REPARSE | 对单个文件重新解析 |
| ROUTE_RETRY | 使用另一解析路线重试 |
| METADATA_REBUILD | 重新抽取分类、实体和关系 |
| CHUNK_REBUILD | 根据新切块策略重新生成 Chunk |
| EMBEDDING_REBUILD | 更换模型后重建向量 |
| VISUAL_INDEX_REBUILD | 更换 ColPali 模型或复杂页面规则后重建视觉索引 |
| INDEX_PUBLISH | 创建并发布索引版本 |
| DELETE_PROPAGATION | 删除文档及所有派生索引 |

### 7.2 文件处理状态

```text
DISCOVERED
→ PREFLIGHT_OK
→ DEDUP_RESOLVED
→ ROUTED
→ CONVERTED（需要时）
→ PARSED
→ QUALITY_CHECKED
→ NORMALIZED
→ MULTIMODAL_ENRICHED（复杂页面必须）
→ ENRICHED
→ CASE_LINKED
→ CHUNKED
→ INDEXED
→ PUBLISHED
```

分支状态：

```text
SKIPPED_TEMPORARY
ALIAS_OF_EXISTING_BLOB
WAITING_HUMAN_REVIEW
QUARANTINED
FAILED_RETRYABLE
FAILED_PERMANENT
DELETED
```

### 7.3 状态转换约束

- 状态只由拥有该阶段 Lease 的 Worker 更新；
- 每次更新使用乐观锁版本号；
- 每个阶段保存开始时间、结束时间、Worker、尝试次数和配置版本；
- `FAILED_RETRYABLE` 可根据错误类型回到当前阶段；
- `FAILED_PERMANENT` 必须由管理员触发重新处理；
- `WAITING_HUMAN_REVIEW` 不进入公开索引；
- 被标记为复杂页面的文档在 `MULTIMODAL_ENRICHED` 完成前不得进入 `INDEXED`；
- `PUBLISHED` 仅表示当前版本已进入某个可查询 Publication；
- 撤回文档时先从新 Publication 排除，再异步清理派生对象。

### 7.4 幂等键

```text
stage_idempotency_key =
  blob_sha256
  + stage_name
  + parser_or_model_version
  + normalized_config_hash
```

若相同幂等键已成功完成，Worker 直接复用产物；若上次运行失败，可以创建新 Parse Run，但不覆盖失败记录。

## 8. 文件预检与安全检查

### 8.1 预检输出

```json
{
  "file_id": "file_xxx",
  "format": "pdf",
  "mime_type": "application/pdf",
  "encrypted": false,
  "page_count": 3,
  "has_text_layer": true,
  "native_text_chars": 1823,
  "chars_per_page": 607.7,
  "image_area_ratio": 0.14,
  "estimated_table_count": 1,
  "estimated_layout_complexity": 0.26,
  "contains_macros": false,
  "contains_embedded_files": false,
  "warnings": []
}
```

### 8.2 安全检查

至少检查：

- 文件头与扩展名是否匹配；
- 是否加密或需要密码；
- 是否存在 Office 宏；
- 是否包含嵌入文件、OLE 对象或外部链接；
- 是否为异常大文件或异常高页数文件；
- 是否为压缩炸弹；
- PDF 是否存在 JavaScript、Launch Action 或异常附件；
- 图片是否超过安全像素限制；
- 解析器是否需要在受限进程中执行。

### 8.3 隔离原则

格式转换和第三方解析器运行在：

- 非特权用户；
- 只读原始输入挂载；
- 独立临时目录；
- 无默认外网访问；
- 受控 CPU、内存、文件大小和运行时间限制；
- 任务结束后销毁临时目录。

云解析能力必须在文件密级允许、管理员开启且调用前完成必要脱敏时才可使用。

## 9. 去重与文件别名

### 9.1 精确去重

精确去重使用原始文件二进制 SHA-256：

```text
相同 SHA-256
→ 只保存一个 Blob
→ 保留多个 Source File 路径别名
→ 解析产物默认复用
```

系统不自动删除原文件。删除属于数据治理行为，不属于知识入库行为。

### 9.2 内容去重

不同文件二进制可能表示相同正文，例如 DOCX 与导出的 PDF。标准化后计算：

- `normalized_text_hash`；
- 标题与正文去页眉页脚后的哈希；
- 表格结构哈希；
- 页面感知哈希；
- MinHash/SimHash 候选相似度。

内容去重只生成候选关系，不直接合并 Document：

```text
exact_content_duplicate
near_duplicate
rendered_copy_of
official_copy_of
```

盖章 PDF 与可编辑 DOCX 即使正文相同，也应作为不同 Document Version 或不同表现形式保留，因为它们的权威性和页面引用能力不同。

### 9.3 重复候选确认

自动确认条件：

- 标准化正文完全一致；
- 标题和文号一致；
- 页面差异只来自印章、签名或格式；
- 所属 Case 一致。

其他近似重复进入人工确认队列。

## 10. 解析路由设计

### 10.1 路由不是文档分类

解析路由回答“怎样得到质量可接受的结构化内容”，文档分类回答“这个文件在业务上是什么”。两者分开实现。

### 10.2 路由输入特征

| 特征 | 说明 |
| --- | --- |
| format | DOCX、DOC、WPS、PDF、XLSX、图片等 |
| has_text_layer | PDF 是否具有可用文本层 |
| chars_per_page | 每页有效字符数量 |
| image_area_ratio | 图片覆盖页面的比例 |
| scanned_page_ratio | 疑似扫描页比例 |
| layout_complexity | 多栏、浮动框、复杂区域数量 |
| table_complexity | 表格数量、合并单元格和跨页程度 |
| text_order_anomaly | 文本读取顺序异常程度 |
| font_encoding_anomaly | 字体编码和乱码异常 |
| native_structure | 是否可读取 OOXML 样式和表格 |
| encrypted | 是否加密 |
| page_count | 页数 |
| file_size | 文件大小 |

### 10.3 路由枚举

```text
NATIVE_DOCX
LEGACY_OFFICE_CONVERT
NATIVE_SPREADSHEET
SEARCHABLE_PDF
SCANNED_PDF_OCR
COMPLEX_PDF_PARSE
IMAGE_OCR
VLM_FALLBACK
MANUAL_REVIEW
UNSUPPORTED
```

### 10.4 第一版规则

```python
def decide_route(profile):
    if profile.encrypted and not profile.password_available:
        return "MANUAL_REVIEW"

    if profile.format == "docx":
        return "NATIVE_DOCX"

    if profile.format in {"doc", "wps"}:
        return "LEGACY_OFFICE_CONVERT"

    if profile.format in {"xlsx", "xls"}:
        return "NATIVE_SPREADSHEET"

    if profile.format in {"png", "jpg", "jpeg", "tiff"}:
        return "IMAGE_OCR"

    if profile.format == "pdf":
        if not profile.has_text_layer:
            return "SCANNED_PDF_OCR"
        if profile.layout_complexity >= COMPLEX_LAYOUT_THRESHOLD:
            return "COMPLEX_PDF_PARSE"
        if profile.text_order_anomaly >= TEXT_ORDER_THRESHOLD:
            return "COMPLEX_PDF_PARSE"
        return "SEARCHABLE_PDF"

    return "UNSUPPORTED"
```

阈值不写死在代码中，由配置中心管理，并通过基准集校准。

### 10.5 路由升级顺序

```text
原生解析
→ 原生解析 + 局部 OCR
→ 全页 OCR + 版面恢复
→ 另一解析器交叉解析
→ VLM 结构化抽取
→ 人工复核
```

每次升级均创建独立 Parse Run。系统保留多个候选结果，由 Quality Gate 选择主结果，不直接覆盖历史产物。

### 10.6 小模型路由器

MVP 不要求训练路由模型。积累以下数据后再训练：

- 预检特征；
- 各解析路线质量得分；
- 单页成本和耗时；
- 人工选择的最佳路线；
- 页面类型标签。

训练目标是选择“满足质量阈值的最低成本路线”，而不是仅预测文档类别。

## 11. 各格式解析方案

### 11.1 DOCX

主要目标：保留原生结构，避免先渲染再 OCR。

解析内容：

- 段落文本；
- Word 样式名称和层级；
- 表格、行、列、合并单元格；
- 页眉、页脚和页码字段；
- 图片及其关系；
- 超链接；
- 批注和修订痕迹状态；
- 文档属性；
- 节、页面大小和页边距；
- 文本框和浮动对象的可用信息。

处理流程：

```text
读取 OOXML
→ 提取原生结构
→ 渲染 PDF/页面图片
→ 对齐段落与页面
→ 结构和视觉一致性检查
→ Normalized Document
```

如果无法精确从 OOXML 得到页码，使用渲染后的页面文本和段落锚点进行对齐。无法可靠对齐时，段落保留 `page_number = null` 并标记需进一步处理，不伪造页码。

### 11.2 DOC 与 WPS

旧格式不直接作为长期解析标准：

```text
原始 DOC/WPS
→ LibreOffice 受限转换
→ DOCX（结构抽取）
→ PDF（页面定位）
→ 结构与页面对齐
```

转换前后记录：

- 转换器版本；
- 转换命令和参数哈希；
- 原始文件哈希；
- 产物文件哈希；
- 页数变化；
- 文本长度变化；
- 表格数量变化；
- 渲染告警。

出现页数骤变、文本大量丢失、中文字体缺失或表格破坏时，Quality Gate 将其标记为不合格，转入 PDF/OCR 路线或人工复核。

### 11.3 可搜索 PDF

处理流程：

```text
提取原生文本和坐标
→ 版面分析
→ 阅读顺序恢复
→ 表格/图片识别
→ 页眉页脚识别
→ 文本层质量检测
→ 必要时局部 OCR
```

不能仅以“存在文本层”判断无需 OCR。部分扫描 PDF 具有低质量隐藏文本层，需检查：

- 可打印字符比例；
- 中文字符比例；
- 文本与页面区域覆盖一致性；
- 字符顺序；
- 字体编码；
- 关键数字识别质量。

### 11.4 扫描 PDF 与图片

处理流程：

```text
PDF 页面渲染/读取图片
→ 方向检测
→ 旋转与去倾斜
→ 去噪和对比度增强（按需）
→ 版面区域检测
→ 中文 OCR
→ 阅读顺序恢复
→ 表格结构识别
→ 印章/签名/手写区域标注
→ OCR 质量评估
```

页面渲染建议在基准集中比较 200、250、300 DPI 后确定默认值。高 DPI 会显著增加内存、GPU 时间和对象存储容量，不应无条件使用最高值。

OCR 输出保留：

```text
text
polygon/bbox
confidence
line_id
reading_order
language
engine
engine_version
```

印章和签名作为视觉区域保存。OCR 识别出的印章文字默认不作为高置信度事实，除非通过正文或其他正式来源验证。

### 11.5 XLS/XLSX

Excel 附件不应只转换成 Markdown 表格。

提取：

- 工作簿和工作表名称；
- 可见/隐藏状态；
- 单元格原值、显示值和公式；
- 合并单元格；
- 表头层级；
- 日期、金额和百分比格式；
- 命名区域；
- 表格范围；
- 注释；
- 页面打印区域；
- 工作表截图或 PDF 预览。

每个工作表生成：

```text
结构化 Cell JSON
面向检索的行记录
面向摘要的 Sheet 描述
可选页面预览图
```

公式同时保存公式文本和缓存值；如果工作簿没有可信缓存值，不执行不受信任宏，也不假设公式结果正确。

### 11.6 复杂表格和混合图文页面

复杂表格与图文页面增强是基础解析路线的一部分，不允许等到 Agent 功能完成后再补建。页面满足任一条件时进入 `COMPLEX_MULTIMODAL_PAGE`：

- 存在跨页表格、嵌套表头或大量合并单元格；
- 页面以表单、呈批表或审批栏为主要内容；
- 文本、图片、印章、手写意见之间的位置关系影响语义；
- OCR/解析器无法稳定恢复阅读顺序；
- 图片或图表包含无法由正文替代的业务信息；
- 文本解析质量通过，但基准查询无法正确召回该页。

处理流程：

```text
页面图片与基础 OCR
→ 页面复杂度分类
→ 表格/版面专用解析
→ 必要时 VLM 结构化增强
→ 生成结构化 JSON、HTML、文本序列化和区域截图
→ ColPali 页面 Patch Multi-Vectors
→ 视觉索引写入
→ 文本、表格、视觉表示用 page_id 对齐
→ 多模态质量门禁
```

复杂页面必须产出：

```text
page_image
page_classification
ocr_or_native_text
layout_blocks
table_or_figure_regions
structured_representation
visual_embedding_metadata
visual_index_status
```

ColPali 负责页面级视觉召回，不替代文本、表格和事实解析。命中视觉页面后，系统使用同一 `page_id` 获取结构化文本、表格或页面区域，必要时再调用 VLM 提取回答所需证据。

如果复杂页面无法得到可靠的结构化表格，但视觉表示构建成功，可以以 `visual_retrievable_but_structurally_unverified` 状态进入受限索引：允许检索和人工查看，不允许其未经人工核验直接成为金额、日期等高风险事实来源。

### 11.7 压缩包

MVP 不自动处理 ZIP/RAR。后续启用时必须：

- 限制解压后文件总量和总大小；
- 拒绝路径穿越；
- 禁止符号链接；
- 检测嵌套压缩；
- 为每个解压文件保留父压缩包关系；
- 将解压产物视为新的 Source File，而不是修改原清单。

## 12. 解析器适配器接口

### 12.1 接口定义

```python
class DocumentParser(Protocol):
    @property
    def name(self) -> str: ...

    @property
    def version(self) -> str: ...

    def supports(self, profile: FileProfile) -> bool: ...

    def parse(
        self,
        input_ref: ObjectRef,
        options: ParseOptions,
        context: ParseContext,
    ) -> RawParseArtifact: ...
```

转换、OCR 和 VLM 使用类似的独立接口：

```text
OfficeConverter
PageRenderer
OCREngine
LayoutAnalyzer
TableExtractor
VLMExtractor
VisualEmbedder
```

### 12.2 RawParseArtifact

第三方解析器输出先封装成原始产物，不直接写入核心 Document 表：

```json
{
  "run_id": "run_xxx",
  "adapter": "docling",
  "adapter_version": "...",
  "config_hash": "...",
  "raw_output_uri": "object://parsed/run_xxx/raw.json",
  "markdown_uri": "object://parsed/run_xxx/document.md",
  "page_images": [],
  "warnings": [],
  "metrics": {
    "elapsed_ms": 0,
    "peak_memory_mb": 0
  }
}
```

Normalizer 再将不同适配器的输出映射为统一模型。

### 12.3 适配器选择

同一 Route 可以配置首选与备选适配器：

```yaml
routes:
  SEARCHABLE_PDF:
    primary: docling_pdf
    fallback:
      - marker_pdf
      - ocr_pdf
  SCANNED_PDF_OCR:
    primary: docling_with_ocr
    fallback:
      - marker_with_ocr
      - vlm_page_extract
```

不能在业务代码中直接判断某个供应商名称，应通过 Route 和 Adapter Registry 解耦。

## 14. 解析质量评估

### 14.1 质量维度

| 维度 | 说明 |
| --- | --- |
| Text Quality | 乱码、缺字、异常字符、文本覆盖率 |
| Layout Quality | 区块检测、坐标、阅读顺序 |
| Table Quality | 表格区域、行列、合并单元格、数值 |
| Metadata Quality | 标题、文号、日期、发文单位 |
| Numeric Quality | 金额、面积、日期、期限等关键字段 |
| Page Alignment | 结构化内容与页码/区域对齐 |
| Multimodal Quality | 复杂页面结构化结果、页面图片和视觉向量是否完整对齐 |
| Cross-format Consistency | DOCX、PDF 或 OCR 结果的一致程度 |

### 14.2 质量得分

初始建议：

```text
quality_score =
  0.25 * text_quality
  + 0.20 * layout_quality
  + 0.20 * table_quality
  + 0.15 * metadata_quality
  + 0.10 * numeric_quality
  + 0.10 * page_alignment_quality
```

如果文档不包含表格，则重新归一化其他权重，而不是将 `table_quality` 固定为 1。

对于 `requires_multimodal_enrichment = true` 的页面，Multimodal Quality 是硬门禁而不是普通加权项。以下任一条件不满足时，文档不能进入完整的 `INDEXED` 状态：

- 页面图片和哈希存在；
- 页面类型已经确认；
- 结构化文本、表格或图文区域已与页面坐标对齐；
- ColPali 多向量产物存在且模型版本可追踪；
- 视觉索引写入成功；
- 使用相同 `page_id` 能在视觉命中结果和原文证据之间回源。

### 14.3 质量分级

| 分级 | 建议阈值 | 行为 |
| --- | ---: | --- |
| PASS | ≥ 0.85 | 自动进入后续处理 |
| PASS_WITH_WARNING | 0.70–0.85 | 可进入索引，但保留警告；高风险文档需人工抽检 |
| RETRY | 0.55–0.70 | 使用备选解析路线 |
| HUMAN_REVIEW | < 0.55 | 不进入有效索引，等待人工处理 |

阈值是初始配置，必须通过基准集校准。

### 14.4 自动质量检查

#### 文本检查

- 有效字符比例；
- Unicode Replacement Character 数量；
- 中文公文中的中文字符比例；
- 重复行和异常空格；
- 页面文本突然为空；
- 字符顺序异常；
- 页眉页脚误混入正文的比例。

#### 结构检查

- 是否识别出标题；
- 文号格式是否合理；
- 标题、主送、正文、附件、落款的相对顺序；
- 标题层级是否跳跃；
- 页面 Block 是否大面积重叠；
- 阅读顺序是否跨栏错乱。

#### 数值检查

- OCR 中数字与原生文本层是否冲突；
- 金额、日期、百分比和单位格式是否合法；
- 同一表格行的列数是否稳定；
- Excel 显示值与原值是否可解释；
- DOCX 与正式 PDF 的关键数字是否一致。

### 14.5 多解析结果选择

若同一文档有多个 Parse Run：

1. 先排除安全失败和结构不完整结果；
2. 按文档类型选择对应质量权重；
3. 比较关键字段正确率，而不只比较字符数量；
4. 若结果分数接近但关键数字冲突，进入人工复核；
5. 选中结果写入 `selected_run_id`；
6. 其他结果保留用于评估，不进入有效索引。

## 15. 文档分类与元数据抽取

### 15.1 分层抽取策略

```text
路径和文件名规则
→ 原生文档属性
→ 正文规则抽取
→ 轻量分类模型/LLM 结构化抽取
→ 一致性校验
→ 低置信度人工确认
```

模型不得覆盖高置信度确定性结果，除非明确给出冲突并进入复核。

### 15.2 路径规则

当前目录结构可提供强提示：

```text
顶层目录        → case_type_hint
年份目录        → year_hint
事项文件夹名称  → document_number_hint + subject_hint
附件目录        → document_role_hint = attachment
复函目录        → document_role_hint = reply
意见汇总文件名  → document_role_hint = opinion_summary
公文稿纸文件名  → document_role_hint = manuscript_sheet
呈批表文件名    → document_role_hint = meeting_form
```

路径只作为提示。内容中的文号、标题和日期用于确认。

### 15.3 文号抽取

文号抽取器需兼容：

- 中文方括号 `〔〕`；
- 普通方括号 `[]`；
- 不规范空格；
- 文件名中的标点和后缀；
- OCR 将括号识别错误的情况；
- 文件夹编号与正文编号不一致的情况。

抽取结果：

```json
{
  "raw": "示例请〔2027〕7号",
  "prefix": "示例请",
  "year": 2027,
  "serial_number": 7,
  "normalized": "示例请〔2027〕7号",
  "confidence": 0.99,
  "source": "document_header"
}
```

### 15.4 文档角色分类

分类特征：

- 文件名和路径关键词；
- 标题；
- 主送和落款；
- 常见正文句式；
- 是否包含“复函”“请示”“意见汇总”等文本；
- 表格结构；
- 与同目录文件的关系。

输出必须符合枚举，不允许模型自由生成新角色。

### 15.5 元数据冲突

来源优先级初始规则：

```text
正式盖章正文
> 正式 PDF 文本/OCR
> DOCX 正文
> 事项文件夹名称
> 文件名
> 文件系统时间
```

若高优先级来源内部存在冲突，系统不自动覆盖，记录 `MetadataConflict`。

## 16. 案件归档与关系构建

### 16.1 Case Seed

当前语料中，每个“类型/年份/事项文件夹”可先建立一个 Case Seed：

```text
case_seed_key =
  normalized_top_category
  + normalized_year
  + normalized_case_folder_name
```

如果能可靠抽取主文文号，则升级为稳定业务键：

```text
business_case_key = normalized_document_number
```

不能仅凭标题相似自动合并两个事项。

### 16.2 归档证据

Case Linker 结合：

- 共同事项目录；
- 文号；
- 征求意见函标题；
- 复函中引用的来函标题或文号；
- 附件列表；
- 会议呈批表中的议题名称；
- 组织、项目、合同等实体重合度；
- 时间顺序。

### 16.3 关系构建规则

示例：

```text
主文正文列出“附件 1”
  + 同目录附件文件名匹配
  → attachment_of

复函标题包含“关于对《X》的复函”
  + X 与征求意见函标题匹配
  → reply_to

意见汇总标题与多个复函主题一致
  → summarized_by

文件名包含“旧版”且正文与定稿高度相似
  → revision_of / superseded_by
```

### 16.4 关系置信度

```json
{
  "relation_id": "rel_xxx",
  "relation_type": "reply_to",
  "source_document_id": "doc_reply",
  "target_document_id": "doc_solicitation",
  "confidence": 0.98,
  "evidence": [
    "标题包含被回复文件全称",
    "文号匹配",
    "所属事项目录一致"
  ],
  "confirmed_by_user": false
}
```

低于配置阈值的关系不进入业务图谱，只作为候选显示。

### 16.5 Case 摘要

Case 归档完成后生成结构化摘要：

```json
{
  "case_id": "case_xxx",
  "subject": "……",
  "case_type": "请示",
  "year": 2026,
  "document_number": "……",
  "organizations": [],
  "topics": [],
  "key_facts": [],
  "requested_actions": [],
  "reply_overview": [],
  "final_status": "unknown",
  "source_document_ids": []

```

Case 摘要必须带来源，不允许脱离文档生成无引用结论。

## 17. 版本识别与权威等级

### 17.1 版本信号

正向权威信号：

- “以此为准”；
- “最终版”“定稿”；
- 正式盖章 PDF；
- 文号、签发、印发信息完整；
- 同目录中修改时间较晚；
- 正式会议或回复材料引用该版本。

历史/非权威信号：

- “旧版”；
- “修改版”“一稿”“二稿”；
- “标黄字为修改内容”；
- `~$` 临时文件；
- 空文件；
- 文号或标题与文件夹明显不一致；
- 被另一版本明确替代。

### 17.2 版本比较

版本比较分三层：

1. 标准化文本相似度；
2. 章节级差异；
3. 实体和关键数字差异。

输出：

```json
{
  "base_version_id": "ver_old",
  "target_version_id": "ver_final",
  "similarity": 0.91,
  "section_changes": [],
  "entity_changes": [
    {
      "entity_type": "money",
      "before": "487000元",
      "after": "543000元"
    }
  ]
}
```

### 17.3 权威评分

权威等级是业务规则，不直接等于模型置信度。初始评分仅用于产生候选：

```text
+ 正式盖章版
+ 文件名包含“以此为准”
+ 正文文号与事项目录一致
+ 被后续正式材料引用
+ 完整落款和日期
- 文件名包含“旧版/一稿/修改版”
- Office 临时文件
- 文号与目录冲突
- 解析质量不合格
```

系统管理员确认后写入不可被自动流程覆盖的 `authority_override`。

### 17.4 使用策略

```text
公文撰写：A/B 级可作为依据，C 级仅用于差异学习
公文审核：A/B 级作为规则和事实依据，C 级用于版本对比
检索问答：默认 A/B 级；用户明确查询历史版本时允许 C 级
```

## 19. Chunk 设计

### 19.1 原则

- 先按业务结构切分，再控制长度；
- 不以固定字符窗口破坏标题、条款和表格关系；
- Chunk 保留父级标题、Case、文档角色和版本信息；
- 页眉、页脚和印发信息作为元数据，不重复进入每个正文 Chunk；
- 关键表格按行或逻辑记录切分，并重复必要表头；
- Chunk 必须可定位回源页面和 Block；
- 不同索引用途允许使用不同 Chunk 表示。

### 19.2 Chunk 类型

```text
case_summary
document_summary
section
paragraph_group
request_item
reply_opinion
meeting_decision
table_summary
table_row
attachment_fact
policy_clause
visual_page
```

### 19.3 分层 Chunk

```text
Case Summary
└── Document Summary
    └── Section Chunk
        ├── Paragraph Chunk
        └── Table Row Chunk
```

检索先召回 Case 或 Document，再在候选范围内召回细粒度 Chunk，减少跨事项噪声。

### 19.4 长度策略

初始建议而非硬规则：

- 普通正文 Chunk：约 300–800 个中文字符；
- 短条款或请示事项：保持原子性，可低于最小长度；
- 长章节：按自然段组合，避免跨二级标题；
- 重叠仅用于缺少自然边界的连续正文；
- 表格按逻辑行生成，不应用字符窗口截断。

阈值应根据 Embedding 模型上下文、检索评估和文档结构调整。

### 19.5 Chunk Schema

```json
{
  "chunk_id": "chunk_xxx",
  "chunk_type": "request_item",
  "case_id": "case_xxx",
  "document_id": "doc_xxx",
  "version_id": "ver_xxx",
  "authority_level": "A",
  "document_role": "main_document",
  "title_path": ["关于某事项的请示", "二、请示事项"],
  "text": "……",
  "embedding_text": "文种：请示\n主题：……\n章节：二、请示事项\n内容：……",
  "keyword_text": "……",
  "page_from": 2,
  "page_to": 2,
  "block_ids": ["block_xxx"],
  "entity_ids": [],
  "content_hash": "...",
  "is_active": true,
  "access_policy_id": "policy_xxx"
}
```

### 19.6 表格 Chunk

表格行的 Embedding 文本必须携带表名和表头：

```text
表格：物业租赁事项调整表
物业：某市场
指标：承租面积
原值：24977平方米
调整后：25546平方米
来源：附件1，第2页
```

不直接对整张超大 HTML 表格生成一个向量。

### 19.7 Chunk 去重

公文红头、页脚、联系人和固定印发信息可能大量重复：

- 页眉页脚默认不进入正文索引；
- 对高度重复的固定模板句设置低信息量标记；
- 保留模板索引，但与事实索引分离；
- 同一 Blob 的多个路径别名不重复生成 Chunk；
- 正式版和旧版保留各自 Chunk，但通过版本过滤控制可见性。

## 20. 索引构建与发布

### 20.1 索引集合

| 索引 | 内容 | 用途 |
| --- | --- | --- |
| case_index | Case 摘要和主题 | 第一阶段事项召回 |
| document_index | 标题、文号、组织、角色 | 精确查询和文档过滤 |
| chunk_keyword_index | 分词后的正文和表格文本 | BM25/关键词召回 |
| chunk_dense_index | Chunk Embedding | 语义召回 |
| entity_index | 组织、金额、日期等 | 精确过滤和事实查询 |
| relation_index | Case/Document 关系 | 复函、附件、版本链查询 |
| visual_page_index | 复杂页面多向量 | 视觉页面召回 |

`visual_page_index` 是基础 Publication 的组成部分。被路由为复杂页面的记录如果缺少视觉向量或视觉索引写入失败，则 Publication 校验必须失败；普通页面可以通过 `visual_index.required = false` 明确跳过，而不是将缺失状态视为成功。

### 20.2 Embedding 输入

Embedding 输入由业务元数据和正文组成，但避免加入无关内部字段：

```text
文种：请示
文档角色：主文
主题：物业续租
章节：二、请示事项
正文：……
```

不加入：

- 原始绝对路径；
- 用户无权看到的密级信息；
- 数据库主键；
- 解析器日志；
- 无意义页眉页脚。

### 20.3 向量幂等

```text
embedding_input_hash =
  embedding_model_id
  + model_revision
  + normalization_version
  + chunk_content_hash
```

相同输入哈希直接复用向量。

### 20.4 Publication

索引更新不直接修改当前线上视图：

```text
构建 staging publication
→ 校验文档数、Chunk 数、权限和向量完整性
→ 运行冒烟查询
→ 原子切换 current publication
→ 延迟清理旧 publication
```

Publication 保存：

```text
publication_id
schema_version
chunker_version
embedding_model_id
source_snapshot_id
document_count
chunk_count
vector_count
created_at
published_at
status
```

### 20.5 删除传播

删除或撤回文档必须使以下内容失效：

- Document Version；
- Page、Block、Table；
- Entity 和 Fact；
- Chunk；
- Keyword Index；
- Dense Vector；
- Visual Vector；
- Case 摘要中的引用；
- 缓存的 Evidence Bundle；
- 依赖该证据的预生成摘要。

优先使用逻辑失效和新 Publication 原子切换，再进行物理删除。

## 24. 任务调度与并发控制

### 24.1 队列划分

```text
queue.discovery
queue.preflight
queue.convert_cpu
queue.parse_cpu
queue.ocr_gpu
queue.vlm_gpu
queue.visual_embed
queue.normalize
queue.enrich
queue.chunk
queue.embed
queue.index
queue.delete
```

### 24.2 并发原则

- 同一 Blob 同一 Stage 同时只运行一个任务；
- 转换和解析任务设置进程级内存限制；
- GPU 任务按显存预算调度；
- 单个大文件不得占满全部 Worker；
- 对来源设置速率限制，避免扫描网络盘影响业务；
- Embedding 批量大小动态调整并记录实际吞吐；
- 用户触发的单文件任务可拥有高于后台全量任务的优先级。

### 24.3 重试策略

| 错误类型 | 行为 |
| --- | --- |
| 临时 I/O 错误 | 指数退避重试 |
| Worker 中断 | Lease 超时后重新入队 |
| 解析器崩溃 | 当前适配器有限重试，再切换备选路线 |
| 资源不足 | 降低并发或批量大小后重试 |
| 文件损坏 | 标记永久失败或人工复核 |
| 文件加密 | 等待密码或人工处理 |
| Schema 校验失败 | 保留原始产物，Normalizer 重试或人工检查 |
| 权限错误 | 不自动扩大权限，直接失败 |

相同适配器、相同配置造成确定性失败时，不进行无限重试。

## 28. 安全与隐私细节

### 28.1 原文与脱敏副本分离

```text
Original Representation
  仅授权用户、审核和引用回源使用

Redacted Representation
  模型输入、开发调试、评估和 Demo 按策略使用
```

脱敏不是直接修改原始解析文本，而是生成具有映射关系的派生表示。

### 28.2 敏感信息类型

- 手机号、座机；
- 身份证号、银行卡号；
- 人员姓名；
- 签名和手写内容；
- 印章；
- 合同价格和财务数据；
- 内部路径、账号和系统信息；
- 未公开项目和法律材料。

### 28.3 模型输入策略

模型网关在调用前检查：

```text
文档密级
模型部署位置
用户权限
任务目的
是否需要原始字段
是否可使用脱敏副本
```

禁止仅因为用户拥有查看权限就自动允许将材料发送到第三方云模型。

### 28.4 日志策略

- 默认记录哈希、ID 和长度，不记录完整正文；
- 调试采样必须显式开启并设置到期时间；
- Prompt/Response Trace 对敏感字段进行脱敏；
- 页面图片不进入普通错误日志；
- 下载和预览原文产生审计事件。

## 29. 测试设计

### 29.1 单元测试

- 文件过滤规则；
- MIME 检测；
- SHA-256 和幂等键；
- 文号标准化；
- 路径提示抽取；
- 金额、面积、日期标准化；
- 版本信号评分；
- Chunk 边界；
- 表格文本序列化；
- 删除传播依赖计算。

### 29.2 Golden File 测试

每种格式选择固定脱敏样本，保存预期：

- 页面数；
- 标题；
- 文号；
- 关键段落；
- 表格行列；
- 关键数字；
- 页面和 Block 定位；
- Parse Quality。

解析器或配置升级后自动比较差异，不允许在未审查差异的情况下更新 Golden 结果。

### 29.3 集成测试

- 目录发现到 Publication 全流程；
- 同一文件重复提交幂等；
- Worker 中断后恢复；
- 解析失败自动切换备选路线；
- 人工确认后重新发布；
- 文档删除后所有索引失效；
- 权限变更后历史缓存失效；
- Embedding 模型变更后并行构建新 Publication。

### 29.4 安全测试

- 路径穿越；
- 恶意 Office 宏；
- PDF JavaScript/附件；
- 压缩炸弹；
- 超大图片；
- Parser 超时和内存耗尽；
- 文档内 Prompt Injection；
- 越权访问页面图片和 Evidence；
- 日志敏感信息泄露。

### 29.5 基准集分层

建议首批选取 80–100 页：

| 类型 | 建议数量 |
| --- | ---: |
| 原生 DOCX 正文 | 15–20 页 |
| 旧版 DOC/WPS 转换 | 10–15 页 |
| 简单扫描公文 | 15–20 页 |
| 盖章复函 | 10 页 |
| 会议呈批表 | 10–15 页 |
| 复杂表格 | 10–15 页 |
| 混合图文附件 | 5–10 页 |

选择样本时覆盖 2025/2026、请示/函、主文/复函/附件和旧版/定稿，而不是随机抽取同一种页面。

## 30. 性能与容量测试

### 30.1 需要测量的指标

- 文件发现吞吐；
- SHA-256 计算吞吐；
- DOC/WPS 转换耗时；
- 每页解析和 OCR 耗时；
- 峰值内存；
- 页面图片平均容量；
- 每个文档产生的 Block、Chunk 和向量数量；
- Embedding 吞吐；
- Publication 构建时间；
- 增量更新延迟；
- 删除传播延迟。

### 30.2 不提前承诺固定吞吐

解析速度受页数、扫描分辨率、表格复杂度、硬件和模型影响。设计文档不设置没有实测依据的“每秒多少页”指标。完成基准集测试后再形成硬件配置与容量规划。

### 30.3 成本控制

- 精确重复 Blob 不重复解析；
- 相同 Embedding 输入复用向量；
- 简单扫描公文不进入 ColPali；
- VLM 只处理路由判定为复杂、低质量或命中后需要精确取证的页面；
- 页面图片使用适合阅读和定位的格式及分辨率；
- 对过期中间产物设置生命周期；
- 全量和在线增量任务使用不同优先级。

## 31. MVP 验收标准

### 31.1 文件发现与去重

- 能扫描指定来源并生成稳定 Manifest；
- 正确过滤 Office 临时文件；
- 完全重复文件只解析一次，但保留全部路径别名；
- 同路径内容更新能够产生新修订记录；
- 文件移动不导致重复解析。

### 31.2 格式处理

- DOCX 能提取段落、样式和表格；
- DOC/WPS 能转换并保留原文件；
- 可搜索 PDF 能提取带页码的文本；
- 扫描 PDF 能通过 OCR 生成可检索文本；
- XLS/XLSX 能提取工作表和表格记录；
- 复杂表格能生成单元格 JSON、HTML、文本序列化和区域截图；
- 混合图文页面能完成页面分类、VLM/版面增强和区域对齐；
- 被标记为复杂的页面能在入库阶段完成 ColPali 多向量和视觉索引写入；
- 解析失败文件不会进入有效索引。

### 31.3 标准化与回源

- 统一文档对象通过 Schema 校验；
- Chunk 能回溯到文档、版本、页码和 Block；
- 页面预览与引用位置一致；
- Parser/Normalizer/配置版本完整记录；
- 普通用户不可看到服务器绝对路径。

### 31.4 业务分类

- 能识别主文、复函、意见汇总、公文稿纸、呈批表和附件；
- 能基于事项目录建立 Case Seed；
- 能识别明显的“旧版”和“以此为准”；
- 低置信度 Case/Version 不自动发布为权威结果；
- 人工修改能够保留审计记录。

### 31.5 索引

- 能生成案件、文档、章节和表格行 Chunk；
- 能构建关键词和 Dense Vector 索引；
- 能构建复杂页面 ColPali 视觉索引，并通过文本查询召回相关页面；
- 视觉召回结果能通过 `page_id` 回源到页面图片、结构化文本和表格区域；
- 必须建立视觉索引的页面缺失视觉向量时，Publication 校验失败；
- 发布前能验证文档、Chunk、向量和权限数量；
- 新 Publication 可以原子切换；
- 撤回文档后查询不可再返回其内容。

## 32. 实施顺序

### 阶段 1：文件清单、状态机与精确去重

- 数据源配置；
- Manifest Snapshot；
- Source File、Blob 和 Job 表；
- 临时文件过滤；
- SHA-256 去重；
- 管理端任务查看。

### 阶段 2：统一 Schema 与基础格式解析

- 解析适配器接口；
- LibreOffice 转换；
- Docling/Marker 对比；
- 统一文档 Schema；
- 页面渲染和基础质量检查；
- 复杂页面分类接口和多模态字段预留。

### 阶段 3：扫描件 OCR、复杂页面增强与 ColPali

- PDF 文本层检测；
- 页面渲染；
- 中文 OCR；
- 复杂表格、表单和混合图文页面识别；
- 表格单元格 JSON、HTML、文本序列化和区域截图；
- VLM 结构化增强；
- ColPali 页面视觉多向量；
- 视觉索引写入和 `page_id` 回源；
- 文本、结构与视觉联合冒烟查询；
- 质量得分；
- 备选路线；
- 人工复核队列。

阶段 3 完成是开发信息检索问答、公文审核和公文撰写功能的前置门禁。

### 阶段 4：案件、文档角色和版本

- Case Seed；
- 路径和标题规则；
- 角色分类；
- 关系构建；
- 版本比较和权威等级；
- 人工确认界面。

### 阶段 5：Chunk、Embedding 与 Publication

- 分层 Chunk；
- 表格行序列化；
- 中文关键词索引；
- Dense Embedding；
- ColPali 视觉索引纳入同一 Publication 校验；
- 原子发布；
- 删除传播。

### 阶段 6：解析基线验收与性能优化

- 对文本、OCR、复杂表格和视觉检索进行完整基准评估；
- 校准复杂页面选择规则和多模态质量门禁；
- 优化文本与视觉结果融合；
- 优化视觉向量存储、查询延迟和批量处理成本；
- 固化第一版可供三个 Agent 使用的解析基线。

ColPali 不要求在文件清单与去重之前实现，但必须在阶段 3 的文档解析基础能力中完成，不能作为三个 Agent 上线后的功能增强项。
